# AGENTS.md

Rules for agents working on IX. Japanese is the director's language. The table is normative in both columns. Identifiers and commands stay in English.

Read `docs/spec/ix-spec-v0.3.md`, section `交渉の拡張仕様（案 v0.3）`, before changing protocol packages. The business numbers above that section are not requirements. `docs/team.md` names who must look at a change.

This revision is the foundation, the term-by-term negotiation machine in `@ix/a2a-ext-negotiation`, A2A-Extensions activation in `@ix/protocol-core`, an in-process publish/query/subscribe relay, mock poster and worker agents in `@ix/agents`, and the replay checks in `@ix/verify`. The agents publish and query term messages through an injected relay board and each rebuilds its state from relay events. `@ix/node` takes an injected event store and does not import `@ix/adapters`. `@ix/adapters` provides the in-memory store and `createLocalRelay`. `@ix/agents` does not import `@ix/adapters`. `@ix/verify` does not import `@ix/agents`. The private trial script `scripts/local-ix.mjs` is the composition root: it may import `@ix/adapters`, `@ix/agents`, and `@ix/jcs`. `scripts/ix-trial-evidence.mjs` may import `@ix/agents`, `@ix/verify`, and `@ix/jcs`. Both read wire JSON with `parseJson`. Relay event `id` is a caller-supplied placeholder. Each mock agent creates a non-extractable Ed25519 key in memory per run (`createEphemeralSigner` in `@ix/identity`), and signs every relay event `sig` (detached JWS over `eventSigningInput`) and every term message `signature` (`{ verification: "jws-eddsa", material }`, a detached JWS over `signingInputExcludingSignature`). The agents and `@ix/verify` refuse an event or message whose signature does not verify against the party's `did:key` (signature stage 2, T25). Each party also has a mock human, the approver: a second in-memory signer with its own `did:key`. A `TermApproval` message's `signature` is made with that party's approver key; every other message and every relay event, including the event that carries the approval, is signed by the agent. The agents and `@ix/verify` refuse an approval not signed by the named party's approver, and refuse peers whose four `did:key` names (two agents, two approvers) are not all different (signature stage 3, D06, T26). `createTermSide` takes `signer` and `approver`; `TermPeers` and `TermSigners` carry `approvers`; `verifyTermTranscript` takes `issuers` and `approvers`. Both read events the same way: by `kind` and the job tag, with `termRelayProfile` passed to `verifyTermTranscript`, and both drop an exact copy of a signed event (same signed content, another `id`) as a duplicate (T25b). `runTermRelay` takes its signers from the caller; it does not create keys itself. The relay node stores events without checking signatures and still reports `signatureVerification: "deferred"`. Term messages carry a hash chain (`prevHash`, `valueHash`, `transcriptHash`, `agreementHash`, plus `manifestSha256` and `sheetSha256`), each the SHA-256 of JCS, which the agents and `@ix/verify` check and apply in chain order (T23). `deploy/local/compose.yaml` binds the trial to `127.0.0.1` and publishes no ports. The verification drive may start that listener only with `IX_BIND=127.0.0.1` and an ephemeral port, and it must stop the processes it starts. `@ix/identity` verifies a detached EdDSA (Ed25519) JWS whose `kid` is an Ed25519 `did:key` (stage 1) and signs with an in-memory key that is never exported or stored (stage 2). Do not implement wire A2A, mandate documents, a real human approval app or the way a person holds an approval key (outside the protocol, D06), relay receipts, key storage, private-key export, inclusion proofs, or MCP tools.

## Human doors

These are not auto-merged, even when CI is green. Stop and name them in the PR. The coordinator asks the director to bring the right person.

- Signatures, keys, mandates, approvals.
- Implementing JCS, choosing the hash, or changing a `prevHash` rule.
- Transparency-log record formats.
- Bumping an extension URI, or adding an event `kind` or tag.
- The legal content of a local rule, spam policy, or anything the spot lawyer is listed for.

## Checks

```bash
pnpm install --frozen-lockfile
pnpm check
```

`pnpm check` is typecheck, lint, boundaries, the guardrail self-test, unit tests, and the conformance suite. The suite passes four items inside a recorded limit and leaves two pending. `pnpm guardrails` lints with the type and comment guards, requires each dummy in `fixtures/guardrails/lint/` to fail for its rule, and runs the dependency checker on `fixtures/guardrails/boundaries/`. Those dummies are outside `pnpm typecheck`, `pnpm lint`, `pnpm test`, and the workspace package set. The verifier entrypoint is `node scripts/verify-ix-node.mjs doctor`, then `drive`, then `cleanup`. Drive writes `artifacts/verify/` and, when the checks pass, starts the relay on `127.0.0.1` and stops it before exiting. Cleanup leaves the evidence directory in place. `artifacts/` is gitignored. The nightly workflow runs `pnpm check`, `pnpm conformance`, and `drive`.

Decisions that are not enforced by a check go in `decisions.tsv`, one row at a time.
