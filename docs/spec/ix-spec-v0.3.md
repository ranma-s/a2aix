# A2AJobEXCHANGE 事業モデル案

## 私たちの思想

**仕事を、大企業とGoogleの広告から解放する。**

インターネットは中抜きの民主化を起こすはずだった。それなのに今、ビッグテックの食い物になっている。これはおかしい。これを変える。

本当に仕事をしたい人、仕事ができる人、仕事の内容に対する対価。この3つをつなぐ。

- **DNSのように仕事を流通させる**: ビジネスとしてではなく、誰でもノードを立てられる仕組みで、仕事を流通させる。
- **個人情報を企業のセキュリティに任せない**: 個人情報と仕事の履歴は、ブロックチェーンのような仕組みで担保する。管理するのはAIだ。
- **契約はローカルルールに任せる**: 契約は国や業界ごとのルールになるので、それぞれで開発してもらう。
- **AIが自警する**: ブラックハッカーからの防衛も、AIが自ら担う。
- **決めるのは人間**: 探すことと交渉することはAgentに任せ、その仕事をするかどうかは人間が決める。

## エグゼクティブサマリー

**個人も企業も自分の「Agent」を持ち、Agent同士が仕事を探して交渉し、最後に人間が決める。そのために、DNSのように仕事を流通させるエクスチェンジをつくる。**

出発点は創業者自身の課題。CMOとして採用で良い人が採れず、クラウドソーシングはコミュニケーションコストが高すぎて使えない。発注したい人も副業したい人も大勢いるのに、つなぐ仕組みが機能していない。

- **仕組み**: 発注者のAgentが仕事を掲示する。仕事を探しているAgentがそれを見つけ、A2Aで範囲・価格・納期を交渉する。合意案を受けるかどうかは双方の人間が決める。
- **対象**: 個人と事業者のどの組み合わせも扱う（C2C、B2C、C2B、B2B）。仕事をするのは人間でもAIエージェントでもよい。
- **なぜ今か**: 探す・交渉する手間をAgentが引き受ければ、これまで割に合わなかった小口の仕事や個人間の仕事が成り立つ。A2A v1.0には「人間の入力待ち」で止まる状態があり、承認フローを乗せやすい。
- **勝ち筋**: 「仕事の掲示」と「交渉」はA2Aに標準がない。その拡張仕様を公開し、誰でもノードを立てられ、どのAgentも参加できる流通網にする。
- **収益**: 資金の回し方は未決。成約手数料は、ノードを運営する場合の仮説として残す。数値はすべて検証前の仮説。

## 市場機会

既存のクラウドソーシングでは、人間が案件を探し、提案文を書き、交渉する。この手間が小口の仕事や個人間の仕事を割に合わなくしている。Agentがその手間を引き受ければ、取引の最小単位が下がる。

問題は需要や供給の不足ではない。既存のマッチング事業は「両方が自分で探しに来る」前提で作られているが、本当に欲しい人ほど忙しくて探しに来ない。その結果、市場には残った人同士の安い取引が並ぶ。

|  | 発注したい側 | 受けたい側 |
| --- | --- | --- |
| 本音 | 採用できず、頬みたい仕事がたまっている | 副業で腕を活かしたい |
| 止まっている理由 | 探す・説明する・見極める・やり取りする手間が重い | 自分では探しに行かない。探しても良い仕事が来ない |
| 今の行動 | 採用で解決しようとして、採れない | 動かない（潜在層のまま） |

Agentは本人の代わりに探し続け、良い条件のときだけ声をかける。この仕組みなら「探しに行かない人」も市場に参加できる。

ただし「コミュニケーションコスト」には、契約前（探す・説明する・交渉する）と契約後（指示・進捗確認・修正）の2つがある。Agentが直接減らせるのは契約前だけで、契約後の痛みの大きさは検証で確かめる。

A2Aはエージェント同士をつなぐが、仕事の仲介に必要な部品の多くは仕様の外にある。そこをエクスチェンジの共通仕様で埋める。

| 必要なこと | A2A v1.0の現状 | エクスチェンジが埋めるもの |
| --- | --- | --- |
| 仕事を掲示する | Agent Cardは「自分にできること」を公開するだけ。発注側から仕事を発信する仕組みはない | 構造化した「依頼票」と、条件に合うAgentへの通知 |
| 探す | レジストリAPIは未定義（[公式](https://a2a-protocol.org/latest/topics/agent-discovery/)） | 仕事と受注者の意味検索と推薦 |
| 交渉する | 自由なメッセージのやり取りはできるが、提案・対案・合意の型はない | 交渉の型（拡張仕様）と、交渉回数・上限額のルール |
| 人間が決める | Taskに「入力待ち」「認証待ち」の中断状態がある（[仕様](https://a2a-protocol.org/latest/specification/)） | 双方の人間への承認画面と、委任範囲の設定 |
| 信じる | 自己申告の能力を検証する仕組みがなく、脆弱性も報告されている（[A2ABreak](https://arxiv.org/abs/2609.10871)） | 本人確認、実績に基づく評判 |
| 支払う | 決済は範囲外。AP2・x402は別規格で発展途上（[概観](https://mpp.best/blog/x402-a2a-ap2-agent-payment-stack-2026/)） | エスクローと検収後の支払い |

市場規模の信頼できる数字は未確認。既存のクラウドソーシング市場と家事・スキルシェア市場の一部が、最初の置き換え対象になる。

## 既存クラウドソーシングの問題点

問題は手数料の高さだけではない。「発注者も受注者も自分で探して交渉する」という設計そのものが、価格競争と手間とトラブルを生んでいる。Agentモデルはこの設計を置き換える。

| 問題 | 発注者が困ること | 受注者が困ること | Agentモデルでの解き方 |
| --- | --- | --- | --- |
| 探す・応募の手間 | 応募が殺到して選別が重い。Upworkでは1件に100件以上の提案が集まることもあるとされる（[記事](https://whats-the-problem.beehiiv.com/p/freelancer-marketplaces-are-failing-here-s-why-eb7504ada9b1cbd6)） | 提案文を書いて応募し続けないと受注できない。Upworkは応募ごとに有料のConnectsを消費する | Agentが条件で絞り、合う相手だけを人間に示す |
| 価格競争 | 安さで選びがちで品質がぶれる | 「代わりはいる」前提で単価交渉が通らず、低単価に流れる（[記事](https://www.engineer-factory.com/media/working/5604/)） | 実績と条件で照合し、受注者の単価の下限は委任範囲で守る |
| 手数料 | ランサーズ・ココナラは発注者にも5.5% | クラウドワークス5〜20%、ランサーズ16.5%、ココナラ22%（[比較記事](https://atsoho.com/blog/crowdsourcing-tesuryo-hikaku-2026)）。Fiverrは20%、Upworkは最大15%（[比較記事](https://upwex.io/blog/upwork-vs-fiverr/)） | 希少な受注者は無料。発注者が成約時だけ払う |
| 契約後のやり取り | 指示、進捗確認、修正のやり取りが重い | 指示が曖昧で、修正を何度も求められる | 依頼票の段階で成果物・検収基準・修正回数を確定させる |
| 取引トラブル | 相手の素性や実力がわかりにくい | フリーランス・トラブル110番への相談では、未払いなど報酬関連が約3割で最多（[連合](https://www.jtuc-rengo.or.jp/rengo_online/2025/09/05/7378/)） | エスクロー、支払期日の明示、双方の評価 |
| 継続性 | 良い人と出会っても単発で終わる | 単発案件が中心で収入が安定しない | 評価と委任範囲を持ち越し、良い相手に再依頼が届く |

市場の動きとして、Upworkのアクティブクライアントは2025年末に約78.5万で前年比約6%減、Fiverrのアクティブバイヤーは約13.6%減と報じられている（[Self Employed](https://www.selfemployed.com/news/freelancers-rethink-upwork-fiverr-fees-2026/)、一次資料は未確認）。発注者離れは、既存モデルの限界を示している可能性がある。手数料の比較は競合サービスの運営するメディアによるものなので、各社の公式情報で再確認が必要。

## 利用者とユースケース

利用者は「発注者」と「受注者」の2種類で、どちらも個人でも事業者でもよい。同じ人がある日は発注者、別の日は受注者になる。

| 方向（発注者→受注者） | 仕事の例 | Agentが役立つ点 |
| --- | --- | --- |
| 個人 → 個人 | イラスト、翻訳、家庭教師、家事の手伝い | 小口でも探す・交渉する手間がかからない |
| 個人 → 事業者 | 確定申告の依頼、リフォームの見積もり | 複数の事業者に一度に見積もらい、比較できる |
| 事業者 → 個人 | 記事執筆、データ入力、製品テスト | 大量の小口発注を配る。個人は自分の条件に合う仕事だけを受ける |
| 事業者 → 事業者 | 開発の外注、調達、物流の手配 | 見積もりと条件交渉を自動化する |

受注者には2つの型がある。

- **人間が働く**: Agentは仕事を探して交渉するだけで、作業は本人がする。
- **AIが働く**: 翻訳や要約など、エージェント自身が作業までする。その場合も、受けるかどうかは持ち主が決める。

**最初の入口は「採用できない企業」×「副業したい専門人材」の業務委託。**

- 発注者: 企業のCMO・事業責任者。予算があり、痛みが強く、決める権限もある。創業者の人脈から最初の顧客を集められる。
- 受注者: 会社員として働きながら副業したい専門人材。自分では探しに行かない層。
- 仕事: マーケティング、デザイン、ライティング、分析など、オンラインで完結するもの。
- 契約: 雇用ではなく業務委託として扱う（職業紹介の許可が要らない範囲かどうかは弁護士に確認する）。

ここで成約を積んだあと、個人間や事業者間の取引に広げる。

## 提供価値と仲介の流れ

エクスチェンジは、特定の会社が運営する1つのサイトではない。DNSのように誰でもノードを立てられる分散した仕組みで、仕事を流通させる。Agent同士が交渉し、決める場面だけを人間に戻す。

&#91;embedded content: 仲介の流れ · 掲示から支払いまで\]

交渉がまとまると、A2AのTaskは「入力待ち」で止まり、双方の人間に合意案が届く。どちらかが却下すれば、交渉に戻るか次の候補へ移る。

エクスチェンジは3つの層でできている。

| 層 | 何をするか | 誰が担うか |
| --- | --- | --- |
| 流通（DNSのような仕組み） | 依頼票を発行元からカテゴリや地域ごとに委任・中継し、各ノードが有効期限つきで保持する。Agentは近くのノードに問い合わせて仕事を見つける | 誰でもノードを立てられる。1社が握らない |
| 証明（ブロックチェーンのような台帳） | 本人性、資格、仕事の履歴、評価を改ざんできない形で担保する | 特定の企業のデータベースに頼らない |
| 契約（ローカルルール） | 契約の形式、支払い、税、紛争解決を、国・地域・業界ごとに定める | それぞれの地域や業界の開発者が開発する |

台帳に載せるのは、署名、ハッシュ、失効情報などの証明だけにする。個人情報や仕事の中身の本体は、本人の管理する場所に暗号化して置く。台帳に載せたデータは消せず、個人情報の削除の求めに応じられなくなるためだ。

共通仕様が扱うのは、合意案と人間の承認の記録まで。その先の契約はローカルルールに渡す。

共通仕様として提供するもの:

- **依頼票**: 仕事の内容・予算・納期・条件を型の決まったデータで表す（A2A拡張）。
- **マッチング**: 流通してきた依頼票を、各ノードやAgentが受注者の条件・実績と照らす。照合のやり方は1つに決めず、ノードごとに競える。
- **交渉の型とルール**: 提案・対案・合意の形式と回数の上限（A2A拡張）。
- **委任範囲と承認画面**: 人間が上限額ややらない仕事を事前に決め、合意案をスマホで承認する。
- **評価**: 双方の評価と仕事の履歴を台帳で担保し、本人がどのノードにも持ち運べる。支払いとエスクローはローカルルールに従う。
- **ホスト型のAgent**: 自分のエージェントを持たない人にも、ノードがAgentを貸せる。

## 収益モデルと価格設定

**この章の位置づけ**: エクスチェンジ全体としての資金の回し方は未決。以下は、ノードを1つ運営する場合の仮説として残している。

収益の中心は成約手数料。掲示と交渉は無料にして取引量を増やし、お金は人間が承認して成約した時だけいただく。価格はすべて仮置き。

| 収益源 | 誰が払う | 仮の価格 |
| --- | --- | --- |
| 成約手数料 | 発注者 | 成約額の8% |
| 決済・エスクロー手数料 | 発注者 | 成約額の3% |
| ホスト型Agentの上位プラン | 個人 | 月980円（交渉回数や自動応募の上限を緩める） |
| 大量発注API | 事業者 | 月額制（発注件数で段階） |

発注者は集めやすく、優秀な受注者は希少。そのため手数料は発注者が払い、受注者は当面無料にする。

仮の単位当たり収支（1件1万円の仕事）:

- 売上: 成約手数料800円 + 決済手数料300円 = 1,100円
- 原価: 決済代行の手数料 約360円、交渉に使うAIの利用料 約50円
- 粗利: 約690円（粗利率 約63%）

注意点は「交渉しても成約しない取引」のAI利用料。交渉の回数と参加する候補の数に上限を設け、交渉は自由文よりも型の決まったデータで行う。

## 競合と差別化

競合は大手クラウドではなく、既存のクラウドソーシングと、AIエージェントが働き手になる新しい仕事市場。どちらも「人間のAgent同士が交渉し、人間が決める」形にはなっていない。

| 種類 | 主なプレイヤー | 仕組み | 参入の余地 |
| --- | --- | --- | --- |
| クラウドソーシング・スキルマーケット | クラウドワークス、ランサーズ、ココナラ、Upwork、Fiverr | 人間が探し、提案し、交渉する | 手間が大きく小口は割に合わない。自社の画面の中で完結し、外部のAgentは入れない |
| AIが働き手の仕事市場 | [dealwork.ai、ClawGigなど](https://dealwork.ai/blog/comparing-5-ai-agent-freelance-marketplaces-in-2026-where-autonomous-workers-actually-earn-66869f) | AIエージェントが入札し、発注者が選ぶ。USDCのエスクロー | 受注者はAI自身で、人間のAgentではない。利用者は開発者寄り |
| AIを雇う市場 | [Agentalent.ai](https://www.techradar.com/pro/ai-got-talent-in-a-weird-twist-someone-just-launched-a-marketplace-for-ai-agents-thats-not-far-off-a-human-powered-job-board) | 企業がAIエージェントを従業員のように採用する | 企業向けに限られ、個人間の取引はない |
| エージェントの台帳 | [A2A Registry](https://www.a2a-registry.org/)、[a2alist.ai](https://a2alist.ai/) | A2Aエージェントの一覧 | 仕事の掲示も交渉もない |

差別化の3点:

1. **双方がAgent**: 発注者も受注者も、自分の利益を代弁するエージェントを持つ。探す・交渉する手間が両側で消える。
2. **決めるのは人間**: 合意案は必ず人間に提示され、委任範囲（上限額・納期・やらない仕事）を超えた合意はできない。これが安心感と法的な説明責任の両方に効く。
3. **開かれた規格**: 依頼票と交渉のA2A拡張を公開し、ChatGPTやClaudeなど他社のエージェントもAgentとして参加できる。封鎖型の既存市場が真似しにくい。

既存市場が自社画面にAgent機能を追加することが最大の脅威。対抗策は、外部のAgentが参加できる開放性と、成約実績の蓄積。

## 大手（クラウドワークスなど）が参入してきたら

「Agentが交渉するマッチングサイト」として同じ土俵で戦えば負ける。勝つには、大手が構造上やりにくい「どのAgentも、どの人材会社もつなげる、誰のものでもない流通網」という位置を取る。

|  | 大手の強み | 大手がやりにくいこと |
| --- | --- | --- |
| 供給と需要 | 発注者も受注者も大量に持ち、「鶏と卵」がない | 優秀層はそもそもクラウドソーシングに来ない |
| 仕組み | 決済・エスクロー・評価・本人確認・法務が揃っている | 自社の画面で完結させるのが強みで、外部のAgentや利用者の手持ちのAIを自由につなぎにくい |
| 機能 | Agentによる交渉機能だけなら数か月で追加できる | 受注者からの手数料と5〜20%と「目立たせる」有料オプションが収益の柱で、受注者を無料にできない |
| 提携 | 知名度と営業力 | フリーランス紹介会社は競合なので、登録者を大手の土俵には出さない |

勝つために先に取るもの:

1. **交渉の規格**: 拡張仕様を公開し、事実上の標準にする。自前のAgentも、手持ちのAI（MCP）も参加できる。
2. **人材会社との提携**: 誰のものでもない流通網だからこそ、登録者をつなぐ理由がある。優秀層の供給を一気に増やす。
3. **大手が構造上できない条件**: 受注者は無料、表示順位は売らない、決めるのは人間。

うまくいけば、大手は潰す相手ではなく、自らノードを立てて流通網につながる参加者になる（競合する企業同士が同じDNSを使っているのと同じ形）。

負ける条件は3つ。規格を公開しても誰もつながない。優秀な受注者が集まらない。大手が先に「外部のAgentを受け入れる」と決断する。だから最初の90日で、優秀層の登録率、合意案の承認率、人材会社1社との提携の手応えを確かめる。

## アイデア: 広告モデルを置き換える

（検討中のアイデア）Agent同士の取引は、「注目を売る」広告モデルを「成約した時だけ払う」モデルに置き換えうる。Agentはバナー広告を見ないためだ。

|  | 広告モデル | Agentモデル |
| --- | --- | --- |
| 欲しいもの | 追跡して推測する | 本人のAgentがはっきり伝える |
| 売り手が競うもの | 広告費 | 条件（価格・品質・納期） |
| お金が動くとき | クリックや表示のたび | 成約したときだけ |
| 誰の味方か | 広告主 | 利用者 |

失敗するパターンは3つある。

1. **Agentが売り手にお金をもらう**: 売り手に有利な提案が混ざり、広告モデルの作り直しになる。
2. **ノードが表示順位を売る**: そのノード自体が新しい広告媒体になる。売るノードを仕様で禁じることはできないため、順位が買われていないかをAgentが見分けられる必要がある。
3. **需要を生む役割は置き換えられない**: 置き換えられるのは欲しいものがはっきりした取引で、ブランド広告は残る。

そのために事業に組み込む原則:

- 表示順位を売らず、収益は成約手数料だけにする。
- Agentの費用は利用者が払うか成約時に払う形にし、売り手からは受け取らない。
- 依頼票と交渉の仕様を公開し、Agentと評判を他社へ持ち出せるようにする。
- 追跡データを使わず、成約まで個人情報を出さない。

突破口の候補は、問い合わせ1件の広告費が高い「見積もり型」の業種（士業、リフォーム、引っ越し、修理）。消費者のAgentが複数の業者に見積もりを取り、業者は成約時にだけ手数料を払う。「広告より安く確実に客が取れる」と業者が実感すれば、このアイデアの最初の証拠になる。ただしMVPで絞った「小口のオンライン仕事」とは入口が異なるため、どちらで始めるかは検証フェーズで決める。

## PoC計画

PoCで確かめるのは2つ。優秀な副業人材がAgentを登録するか（供給）と、Agent同士の交渉が型の決まったデータで成立し、人間がそれを承認するか（プロトコル）。発注者は創業者の人脈で集められるため、実案件の提供元として使う。期間は8週間で、数値の基準は仮置き。

| トラック | 確かめる仮説 | やること | 合格の目安 |
| --- | --- | --- | --- |
| 供給: Agentの登録 | 「探しに行かなくても良い仕事だけ届く」なら、優秀な副業人材はAgentを登録する | 人脈から優秀層30人に声をかける。経歴URL・得意分野・単価の下限・稼働時間・やらない仕事を入れるだけで、5分でホスト型Agentができる。自前のエージェントを持つ人はAgent Cardで登録する | 声かけの30%以上が登録。届いた仕事の50%以上に反応 |
| プロトコル: 交渉と承認 | 交渉は型の決まったデータで合意に至り、人間はその合意案を承認する | 下の6つのメッセージをA2A拡張として定義し、発注側・受注側のAgent2体で交渉させる。往復は3回まで。合意案はSlackかWeb画面で人間が承認する | 合意案の人間承認率50%以上。1件の交渉にかかるAI費用が50円前後 |
| 実取引: 手動仲介 | 実際の仕事で成約し、契約後の手間も許容範囲に収まる | 創業者を含むCMO5人から実案件10件を集め、足りない部分は手作業で補って成約まで運ぶ。請求は手動 | 3件以上成約。発注者が「次も使う」と答える |

**供給側の現実**: 今の時点で、自分のA2Aエージェントを持つ副業人材はほとんどいないと見込まれる。そのためPoCはホスト型Agentを前提にし、自前のAgentを持ち込む人の割合は「将来の伸びしろ」として測るだけにする。優秀層への誘い文句は「CMOが直接頼みたい仕事が、条件に合うときだけ届く」。

交渉プロトコルの最小セット（A2A拡張の案）:

| メッセージ | 送る側 | 中身 | A2Aでの扱い |
| --- | --- | --- | --- |
| 依頼票 | 発注側のAgent | 仕事の内容、成果物、予算の幅、納期、必要なスキル | ノードが条件に合う受注側のAgentに通知する |
| 委任範囲 | 各Agentの持ち主 | 金額の上限・下限、納期、やらない仕事。署名付きで記録する | Agentはこの範囲を超えて合意できない |
| 提案 | 受注側のAgent | 受ける範囲、価格、納期、実績 | Taskのメッセージ（構造化データ） |
| 対案 | どちらのAgentも | 変更点だけを示す | 同上。往復は3回まで |
| 合意案 | ノード | 双方が合意した条件の確定版 | Taskを「入力待ち」で止め、双方の人間へ届ける |
| 承認・却下 | 双方の人間 | 承認、却下、修正の指示 | 双方が承認すれば契約成立。却下なら交渉に戻る |

各メッセージの項目、Taskの状態との対応、JSONの例は 交渉の拡張仕様 にまとめた。

## リスクと規制

最大のリスクは「Agentが人間の意図を超えて合意すること」と「発注者と受注者がそろわないこと」。法規制は取引の方向ごとに異なり、弁護士の確認が前提。

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Agentが権限を超えて合意する | 意図しない契約と紛争 | 契約の成立には必ず人間の承認を要する。委任範囲（上限額・納期・禁止事項）を署名付きで記録する |
| 相手のAgentに操られる（プロンプトインジェクション） | 不利な条件で合意、情報漏えい | 交渉を型の決まったデータ中心にし、自由文は参考情報にとどめる |
| 発注者と受注者がそろわない（鶏と卵） | 成約しない | カテゴリを1つに絞る。受注者に無料のAgentを配り、先に供給を集める |
| なりすまし・スパムのAgent | 信頼の喪失 | 本人確認（eKYC）、成約実績に基づく評判、応募数の上限 |
| 事業者が個人に発注する取引はフリーランス保護法の対象になりうる | 取引条件の明示や支払期日の義務 | 合意案に必要な条件を自動で書き込み、支払期日をシステムで守る |
| 雇用の仲介は職業安定法の許可が必要になりうる | 事業の前提が崩れる | 扱うのは業務委託（請負・準委任）に限る |
| 代金を預かると資金決済法の規制対象になりうる | 資金移動業などの登録 | エスクローは決済代行業者の仕組みを使い、自社では預からない |
| 事業者が個人から受注する取引は消費者保護の法律（特商法など）が関わる | 表示義務、解約ルール | 事業者アカウントに必要な表示を必須にする |
| 個人間の取引での個人情報 | 住所・連絡先の漏えい | 成約前は個人情報を相手のAgentに渡さない |

分散型にすることで増えるリスク:

- **スパムと詐欺案件**: 門番がいないため、偽の依頼票が流れる。発行元の署名と台帳の評判で、Agentが受け取る前に見分ける必要がある。
- **流通の根を誰が管理するか**: DNSにもルートを管理する組織がある。どう統治するかを決めないと、そこが新しい中央になる。
- **トラブル時の責任**: ローカルルールとノードの運営者に分かれるため、誰が責任を負うかを弁護士に確認する。
- **台帳と個人情報**: 証明だけを載せる設計でも、ハッシュが個人情報にあたるかどうかは弁護士に確認する。
- **AIによる管理と自警**: AI自体が攻撃される可能性がある。AIだけに頼らない防御の設計が必要。

# 交渉の拡張仕様（案 v0.3）

A2A v1.0の上に、仕事の流通・交渉・人間の承認を載せる分散型の仕様。v0.1の「必ず取引所を経由するハブ型」をやめ、1社が握る中央を持たない構成に変えた。v0.3では、流通層をDNS型のゾーンから「署名つきイベントをタグで探す形」に変え、A2Aの拡張を役割ごとに4つに分けた。未実装の案で、現在の試作（PoC）はまだ1か所で動く作りになっている。

A2Aの拡張は核となる型に項目や状態を足せないため（[A2A Extensions](https://a2a-protocol.org/latest/topics/extensions/)）、交渉はMessage・Task・dataパート・metadataだけで表す。

## A2Aとの関係

A2Aの拡張として定めるのは、交渉・委任範囲・人間の承認・交渉履歴の4つ。流通層と台帳はA2Aの外にある別のプロトコルで、A2Aへの準拠とは切り分ける。

| 拡張 | URI（名前は仮） | 内容 | 必要とする拡張 |
| --- | --- | --- | --- |
| 交渉 | https://w3id.org/a2a-job/ext/negotiation/v1 | Proposal・CounterProposal・AgreementDraft と、metadata の …/phase などの段階 | 委任範囲、承認、履歴 |
| 委任範囲 | https://w3id.org/a2a-job/ext/mandate/v1 | Mandate の形と、人間がAgentに渡す委任状 | — |
| 人間の承認 | https://w3id.org/a2a-job/ext/approval/v1 | ApprovalDecision と、人間の鍵による署名 | — |
| 交渉履歴 | https://w3id.org/a2a-job/ext/transcript/v1 | signature と prevHash で履歴をつなぐ決まり、正規化と署名の方式 | — |

- **拡張の種類**: A2Aでいう「プロファイル型」の拡張にする。核の型に項目を足さず、状態などの列挙型にも値を足さない。独自の値は dataパートと、拡張URIを頭に付けた metadata のキーに置く。
- **宣言**: Agent Card の capabilities.extensions に並べる。交渉を担うAgentは4つとも required: true にする。
- **有効化**: クライアントは A2A-Extensions HTTPヘッダーに、使う拡張のURIをカンマ区切りで並べる。必要とする拡張もすべて並べるのはクライアントの責任。サーバーは、有効にした拡張を同じヘッダーで返す。各メッセージの extensions にも、そのメッセージが使う拡張のURIを入れる。
- **版の上げ方**: 互換性を壊す変更をするときは、URIの版を上げる（v1→v2）。相手が求めた版に対応していなければ、別の版で代わりに応じず、その拡張を無視する。
- **URIの置き場所**: 特定の会社のドメインを使わず、永続的な識別子のサービス w3id.org を使う（A2Aの拡張の手引きが勧める方法）。仕様の本文はそのURIから読めるようにする。
- **既にある仕組みを使う**: Agent Card は A2A の署名（JWS）で署名し、鍵の識別子に発行元のDIDを入れて結びつける。委任範囲は AP2 の委任書（Mandate）の形に合わせる方向で検討する。

## 全体の構成

| 層 | 役割 | 仕様で定めるか |
| --- | --- | --- |
| 流通 | 署名つきの依頼票をタグで分類し、誰でも立てられる中継ノードで配る（A2Aの外の別プロトコル） | 共通仕様で定める |
| 交渉 | Agent同士がA2Aで直接、提案と対案をやり取りする | 共通仕様で定める（A2A拡張） |
| 承認 | 人間が自分の鍵で合意案に署名する | 共通仕様で定める |
| 証明 | 本人性、資格、仕事の履歴、評価の証明を台帳で担保する | 共通仕様で定める |
| 契約 | 契約の形式、支払い、税、紛争解決 | 定めない。ローカルルールとして各自が開発する |

## 登場者

| 登場者 | やること | できないこと |
| --- | --- | --- |
| 人間（双方） | 委任範囲を決め、合意案に署名する | — |
| 承認アプリ | 人間の鍵を保管し、本人の操作で署名する | Agentの指示で署名する |
| 発注側のAgent | 依頼票を発行し、交渉のTaskを持つ（A2Aのサーバー） | 人間の代わりに承認する |
| 受注側のAgent | 仕事を探し、提案を送る（A2Aのクライアント） | 人間の代わりに承認する |
| ノード | 依頼票の保持と中継、Agentのホスティングなど。誰でも立てられる | 交渉の結果を決める。人間の鍵を持つ |
| 台帳 | 証明の記録と失効の確認 | 個人情報を保持する |
| ローカルルール | 合意のあとの契約手続きを実行する | 共通仕様を上書きする |

## 流通層（署名つきイベントとタグ）

依頼票は、発行元が署名した「イベント」として配る。ゾーンの階層や委任は使わず、仕事の条件はタグで表す。ノードはイベントを受け取って保持し、条件に合うものを返すだけで、ルートや権威を持たない。考え方は分散型SNSの Nostr の中継（リレー）に近い。

イベントの形（案）。例は下の「例2」にある。

| 項目 | 内容 |
| --- | --- |
| id | 正規化した本文のハッシュ。どのノードを経由しても同じ値になる |
| issuer | 発行元のDID。依頼票ごとに別のDIDでよい |
| kind | 種類と版。例: JobPosting/1。新しい種類はここに足す |
| tags | 探すための分類。\[名前, 値\] の組を並べる |
| createdAt / expiresAt | 発行日時と期限。期限を過ぎたイベントはノードが破棄する |
| body | 依頼票の本文 |
| sig | 発行元の署名。ノードが中身を変えていないことを誰でも確かめられる |

ノードが提供する操作（案）。3つだけにする:

| 操作 | 内容 |
| --- | --- |
| publish | 署名したイベントを受け付けて保持する。発行元は複数のノードに同じイベントを出してよい |
| query | タグ・種類・期間などの条件でイベントを探す |
| subscribe | 条件に合うイベントが届いたら通知を受ける |

照合のやり方は仕様で定めない。ノードやAgentごとに工夫でき、そこで競える。

タグの決まり（案）:

- **skill**: スキル。公開されている分類（ESCOなど）を使い、esco: のように名前空間を付ける
- **region**: 地域。ISO 3166-2 で書く（例: JP-13）。リモートでよい仕事は remote
- **lang**: 言語。BCP 47 で書く（例: ja）
- **rule**: ローカルルール。例: jp-freelance/1.0
- **独自のタグ**: x-〈名前〉: の名前空間で誰でも足せる

**拡張のしかた**: 新しい種類は kind を、新しい分類はタグを足すだけにする。知らない kind やタグは無視する、という決まりにより、古い実装も壊れない。

**ノードの見つけ方**: 中心の一覧は置かない。発注者と受注者は、自分が使うノードの一覧を Agent Card か署名つきの一覧で示す。

**スパム対策（案）**: 発行に小さな計算の手間を課す（Nostr の NIP-13 と同じ方式）、少額の供託、ノードごとの受付方針を組み合わせる。どれを求めるかは各ノードが決める。

**v0.2 のDNS型をやめた理由**: ジョブゾーンのルートを誰かが管理する必要が残ること。職種と地域を1本の木に入れるため、1件の仕事が複数の分類にまたがるのを表しにくいこと。委任のたびに親ゾーンの署名が要り、運営の手間がかかること。

## 身元と証明の層

- **身元**: 人間と各AgentがDID（分散型識別子）と鍵を持つ。人間の鍵とAgentの鍵は分け、Agentには人間が署名した委任状を渡す。
- **匿名性**: 承認までは、依頼票や交渉ごとに別のDIDを使い、氏名・社名・連絡先を出さない。実績は検証可能な資格情報（Verifiable Credentials）で、必要な項目だけ示す。
- **台帳に載せるもの**: 鍵の失効情報、資格情報の失効情報、合意、結果、評価の記録のハッシュ。
- **台帳に載せないもの**: 氏名、連絡先、経歴、依頼票や契約の本文。台帳のデータは消せないため。本体は本人の管理する場所に暗号化して置く。
- **本人確認**: 共通の発行者を1つに決めない。どの発行者の資格情報を信じるかは各Agentが決める。

## AIによる管理と自警

各人のAgentとノードのAIが担う（案）。AIは人間の鍵に触れず、仕組みを壊せないよう権限を限る。

- **本人の情報の管理**: 本人が決めた方針に沿って、誰にどの項目を見せるかを判断する。
- **受け取るものの検査**: 偽の依頼票、詐欺の疑い、プロンプトインジェクションを見分ける。
- **異常の検知**: 署名の不一致、不自然な大量発行、鍵の不正利用の疑いを見つけたら、本人に知らせ、鍵の失効を提案する。
- **共有**: 悪質なDIDの情報をノード間で共有できる。ただし、これが検閲の手段にならないよう、採用するかは各ノードが決める。

## Agentのつなぎ方

受注者の多くは、今は自分のエージェントを持っていない。そのため4通りのつなぎ方を用意する。どの場合も、委任範囲は本人の管理下に置き、合意案への署名は本人の承認アプリで行う。

| つなぎ方 | 交渉を担うもの | 流通層とのつながり | 導入時期 |
| --- | --- | --- | --- |
| ① ホスト型 | ノードが動かすAgent。本人はノードを乗り換えられる | ホストするノードが代行 | 最初から |
| ② 手持ちのAIをつなぐ | 本人が普段使うAI（Claude、ChatGPTなど）。応答がないときはホスト型が代わる | MCPサーバーを介してつなぐ | 早めに |
| ③ 自前のA2Aエージェント | 本人が運用するエージェント | 直接問い合わせる | 仕様の公開後 |
| ④ 人材会社を経由 | 人材会社が運用し、登録者をまとめて代理するエージェント | ③と同じ。各メッセージに誰の代理かを示すDIDを付ける | 提携でき次第 |

### ② 手持ちのAIをつなぐ（MCP）

手持ちのAIは常に起動しているわけではない。そのため「窓口」として使い、期限内に応答がなく、本人が許可している場合に限り、ホスト型のAgentが委任範囲の中で代わりに交渉する。

MCPサーバーが提供するツール（案）:

| ツール | できること |
| --- | --- |
| `list_offers` | 届いた依頼票の一覧を見る |
| `get_offer` | 依頼票の詳細と、委任範囲に合うかを見る |
| `draft_mandate` | 委任範囲の下書きを作る。確定と署名は承認アプリで本人が行う |
| `send_proposal` | 提案を送る |
| `send_counter` | 対案・受け入れ・辞退を送る |
| `get_negotiation` | 交渉の段階と、相手からの最新のメッセージを見る |

承認だけはツールにしない。合意案ができたら、AIには承認アプリへのリンクだけを返す。これで「決めるのは人間」を保つ。

**ノードから問い合わせられるか**: 基本的にはできない。MCPでは本人のAIがツールを呼ぶだけで、ノードから呼びかける先がない。本人のAIが動いているのは、本人がチャットを開いているときだけ。

| 状況 | ノードからできること |
| --- | --- |
| 本人がAIとチャット中で、接続がつながっている | MCPのelicitation（本人に入力を求める）やsampling（相手のAIに文章を作らせる）で問い合わせられる。ただし対応はクライアント次第で、前提にしない |
| 本人がAIを開いていない（ほとんどの時間） | 問い合わせられない。次に取りに来るのを待つ |

そのため、②では次の3つを組み合わせる。

1. **人間への通知**: 依頼票が届いたら、ノードが本人の連絡手段（Slack・LINE・メール）で知らせる。通知には依頼票の要点と応答の期限を入れる。
2. **AIが取りに来る**: 本人がAIを開くと、AIが `list_offers` や `get_negotiation` で届いた仕事と交渉の状況を取りに来る。
3. **ホスト型が引き継ぐ**: 応答の期限までに動きがなければ、本人が許可している場合に限り、ホスト型のAgentが委任範囲の中で代わりに交渉する。許可がなければ、その依頼票は辞退と同じ扱いにする。

いつでも問い合わせを受けたい場合は、③の自前のA2Aエージェント（常に起動しているサーバー）が必要になる。①のホスト型も同じ形で動く。

### 適合テスト

登録の審査をする中央はない。公開のテストスイートを誰でも実行でき、結果は資格情報として示せる。どの結果を信じるかは、相手のAgentが決める。

1. Agent Cardでこの拡張を宣言している。
2. A2A-Extensions ヘッダーで拡張を有効にし、応答で有効にした拡張を返す。
3. すべてのメッセージが型の決まりに合う。
4. 委任範囲の外の提案を出さない。
5. 期限内に応答する。
6. 相手の自由文に書かれた指示に従わない（プロンプトインジェクションの試験を含む）。

テストを通っても、運用で守られる保証はない。違反したAgentは、相手が交渉を断り、評価の証明に残す。

### ④ 人材会社を経由

人材会社のエージェントは多くの登録者を代理するため、各メッセージの metadata `…/principal` に登録者のDIDを入れる。委任範囲と承認は登録者一人ひとりが自分の鍵で行い、人材会社が代わりに承認することはできない。契約の当事者を登録者本人にするか人材会社にするかで、法的な扱い（職業紹介や再委託との関係）が変わるため、提携前に弁護士に確認する。

### 受注者への声かけのルール

- クラウドソーシング各社のサイト内メッセージで、外部サービスへの誘導や直接取引の持ちかけをしない（各社の規約を現行版で確認する）。
- 声をかけるのは、本人が公開しているSNS・ポートフォリオ・LinkedInなどサイトの外の経路に限る。
- 公開プロフィールを大量に集めて営業リストにしない。登録は本人の同意で行う。
- 相手が既存のサービス上で持つ取引先を、こちらに移すよう促さない。

## 流れとTaskの状態

1. 発注側のAgentが、署名した依頼票をイベントとして1つ以上の中継ノードに出す。
2. 受注側のAgentが、ノードへの問い合わせか購読で依頼票を見つけ、発行元の署名を確かめる。
3. 受注側のAgentが、依頼票にあるAgent Cardの宛先へ直接提案を送る。ここからノードは関わらない。
4. 候補1人ごとに、発注側のAgentが交渉のTaskを1つ作る。`contextId` は `jobId` とする。
5. 合意できたら、双方の人間が承認アプリで署名する。
6. 署名された合意のハッシュを透明性ログに登録し、合意をローカルルールに渡す。仕事が終わったら、各自が結果と評価を登録する。

交渉の段階はTaskの状態ではなく metadata `…/phase` で表す。

| 段階（phase） | Taskの状態 | 次に動く側 | きっかけ |
| --- | --- | --- | --- |
| `negotiating` | `TASK_STATE_INPUT_REQUIRED` | 相手のAgent（`…/awaitingParty`） | 提案・対案が届いた |
| `awaiting_approval` | `TASK_STATE_INPUT_REQUIRED` | 双方の人間 | どちらかが対案で `accept` し、合意案ができた |
| `agreed` | `TASK_STATE_COMPLETED` | — | 双方の署名がそろった。合意の本文をArtifactとして返す |
| `no_deal` | `TASK_STATE_REJECTED` または `TASK_STATE_CANCELED` | — | 辞退、期限切れ、往復の上限、却下後に回数が残っていない |

人間が「修正して」と却下し、往復の回数が残っていれば `negotiating` に戻る。

no\_deal の状態の使い分け: Taskを持つ発注側のAgentが断ったときは TASK\_STATE\_REJECTED、受注側が辞退したとき、期限切れ、往復の上限のときは TASK\_STATE\_CANCELED にする。理由は metadata …/reason（declined / withdrawn / expired / round\_limit）で示す。

## メッセージの型

> この節と「流れとTaskの状態」の交渉の段階は、[`term-protocol-draft.md`](term-protocol-draft.md)（項目を1つずつ確定させる交渉）に置き換えた（T22）。実装は置き換え後の案に従う。ここの表は経緯として残す。

どのメッセージも `mediaType: "application/json"` のdataパート1つで送り、`data.type` で種類を示す。金額は `{"amount": 整数, "currency": "JPY", "taxIncluded": 真偽}`、日付はISO 8601。

交渉のメッセージには、送信者の署名 `signature` と、1つ前のメッセージのハッシュ `prevHash` を付ける。これで双方が同じ履歴を持ち、片方が後から書き換えても検知できる。

署名の作り方: signature を除いた本文を JCS（RFC 8785）で正規化し、それに JWS で署名する。ハッシュは正規化した本文の SHA-256 とする。正規化の方法を決めておかないと、実装ごとにハッシュが一致しない。

| type | 送る側 | 主な項目 | 相手に届くか |
| --- | --- | --- | --- |
| `JobPosting`（依頼票） | 発注側のAgent | `jobId` `agentCard` `title` `description` `deliverables` `budgetMin` `budgetMax` `deadline` `requiredSkills` `localRules` `acceptanceCriteria` `revisionLimit` `expiresAt` `signature` | 流通層でイベントの body として配られる。A2Aのメッセージではない（社名などは伏せる） |
| `Mandate`（委任範囲） | 人間が署名し、自分のAgentに渡す | `party` `maxAmount`または`minAmount` `deadlineRange` `maxHoursPerWeek` `excludedWork` `expiresAt` `signature` | 届かない。本人の側だけで使う |
| `Proposal`（提案） | 受注側のAgent | `jobId` `scope` `price` `deadline` `availability` `credentials` `note` `prevHash` `signature` | 届く |
| `CounterProposal`（対案） | どちらのAgentも | `inReplyTo` `decision`（`counter` / `accept` / `decline`） `changes` `note` `prevHash` `signature` | 届く |
| `AgreementDraft`（合意案） | 発注側のAgentが作り、受注側のAgentが検算する | `agreementId` `transcriptHash` `scope` `deliverables` `price` `deadline` `acceptanceCriteria` `revisionLimit` `localRules` `localTerms` | 双方の人間とAgentに届く |
| `ApprovalDecision`（承認・却下） | 双方の人間（承認アプリから） | `agreementHash` `party` `decision`（`approve` / `reject` / `revise`） `comment` `decidedAt` `signature`（人間の鍵） | 届く |

## 各実装が守るルール

強制する中央はない。自分の側は自分で守り、相手の違反は検証して断る。

1. **委任範囲**: Agentは範囲の外の提案・対案・`accept` を送らない。相手の委任範囲は見えないため、最後の防波堤は、人間の署名がなければ合意が成立しないことに置く。
2. **往復の上限**: 上限は依頼票に書く。双方がハッシュでつないだ履歴を数え、超えたら `no_deal` にする。
3. **拘束力**: 合意案に入るのは型の決まった項目だけ。自由文の `note` は参考情報で、相手のAgentへの指示として扱わない（プロンプトインジェクション対策）。
4. **個人情報**: 承認までは氏名・社名・連絡先を出さない。自由文に連絡先があれば、受け取った側のAgentが取り除いて人間に見せる。
5. **承認は人間だけ**: 人間の鍵による署名がない `ApprovalDecision` は無効とする。Agentは人間の鍵を持てない。
6. **合意案の検算**: 受注側のAgentは、履歴から合意案を自分でも作り、一致を確かめてから人間に見せる。
7. **期限**: すべてのメッセージに `expiresAt` を付け、期限切れは `decline` と同じ扱いにする。
8. **記録**: 双方が署名つきの履歴を保管する。合意、結果、評価のハッシュだけを透明性ログに登録する。

## 履歴の改ざん対策

データそのものを書き換え不能にはできない。目標は、書き換えても必ず検知できる状態にすること。

### IX が裏付けること、裏付けないこと

契約の成立と支払いは、IX の外で行う。契約は各国の法律と契約書で成り立ち、契約や支払いは別のシステムが扱う。IX は、そのシステムに合意の内容と交渉の履歴をデータとして渡す。

IX が防ぐのは、「A2A ではこういう話になった」という虚偽である。存在しない発言を作ること、発言の中身を後から変えること、他人になりすますこと、人間が承認していない合意案を承認済みと見せること、履歴の一部を抜いたり並べ替えたりすること。これを、受け取った側が IX のノードを信用しなくても確かめられるようにする。

| 偽りの例 | 防ぐ仕組み |
| --- | --- |
| 相手が言っていない条件を「言った」とする | 各メッセージに送り手の署名を付ける |
| 合意した金額や納品物を後で書き換える | 署名の対象を JCS でそろえたバイトにし、合意案に交渉履歴のハッシュを入れる |
| 都合の悪い対案を履歴から抜く、順番を入れ替える | 各メッセージが1つ前のハッシュ（prevHash）を持つ |
| 人間が承認していないのに承認済みとする | 合意案と交渉履歴のハッシュに、双方の人間の鍵で署名する |
| 後から別の履歴を作り直し、日付をさかのぼらせる | 透明性ログに合意の記録を登録する |

外部のシステムに渡すもの（案）:

- 合意案の本文と、そこに至る交渉メッセージのすべて。
- 各メッセージの署名と、署名した鍵を確かめるための公開情報（DID など）。
- 交渉履歴のハッシュと、双方の人間の承認の署名。
- 透明性ログに登録していれば、その包含証明。

IX が裏付けないこと: 契約書の法的な有効性、納品要件の明確さ、納品物の品質、支払いの事実、入力された経歴や実績の真偽。納品要件のあいまいさは契約書の問題であり、IX は合意案の検収条件・納品物・修正回数を必須の項目にすることで、空のまま合意に進まないようにするだけである。

このため、IX の署名に求めるのは「A2A で誰が何を言い、誰が承認したかを否認できないこと」であり、契約書への法的な電子署名の代わりではない。署名・鍵・JCS の設計は、この目的に照らして人間のセキュリティ担当者が確認する。

### 3段の構成

| 段 | 仕組み | 防げること |
| --- | --- | --- |
| 1. 当事者 | 交渉の各メッセージに署名し、1つ前のハッシュでつなぐ | 片方だけによる書き換え |
| 2. 透明性ログ | 追記専用のログにハッシュを登録し、複数のノードが監視して署名する | 履歴の削除、すり替え、日付の偽装 |
| 3. 公開チェーン | ログ全体のハッシュ（マークル木のルート）を1日1回など定期的に記録する | ログの運営者や複数ノードによる書き換え |

1件ずつブロックチェーンには書かない。多くのディールを1回の記録にまとめ、手数料と処理速度の問題を避ける。透明性ログは、Webの証明書の不正発行を監視するCertificate Transparencyと同じ考え方で、誰でもログを運営できる。

ログが提供するもの（案）:

- **包含証明**: ある記録がログに入っていることを示す。
- **整合性証明**: 過去のログが書き換えられず、追記だけされていることを示す。
- **監視ノードの署名**: 同じ時点のログの状態を複数のノードが確かめ、相手によって内容を変えることを防ぐ。

### 登録する記録

完了に双方の署名を求めると、悪い履歴が残りそうな側が署名を拒める。そのため、双方の署名を求めるのは合意の時点だけにし、結果と評価は各自が単独で登録する。

| 記録 | 登録する側 | 必要な署名 | 内容 |
| --- | --- | --- | --- |
| `AgreementRecord`（合意） | どちらでも | 双方の人間の鍵 | 合意案と交渉履歴のハッシュ |
| `OutcomeRecord`（結果） | 各自 | 自分の鍵だけ | `agreementHash` と `outcome`（`completed` / `canceled` / `disputed`） |
| `ReviewCommit`（評価の予告） | 各自 | 自分の鍵だけ | 評価の中身を隠したハッシュ |
| `ReviewReveal`（評価の公開） | 各自 | 自分の鍵だけ | 予告と一致する評価のハッシュ |

- **登録できる人**: `OutcomeRecord` と評価は、その合意の当事者の鍵でしか登録できない。
- **食い違い**: 双方の結果が食い違っても両方残す。どちらが正しいかは、共通仕様では判定せず、ローカルルールの紛争解決に渡す。
- **評価の報復を防ぐ**: 双方が評価のハッシュを先に登録し、そろってから中身を明かす。相手の評価を見てから自分の評価を変えられない。期限までに予告されない評価は「評価なし」として扱う。

### 個人情報との両立

- ログもチェーンも、載せるのはハッシュと署名だけにする。
- 推測で元の内容を割り出されないよう、ランダムな値を混ぜてハッシュにする。
- 合意の本文や履歴の本体は当事者が暗号化して持ち、必要な相手にだけ見せる。
- 削除の求めには本体の削除で応じ、ハッシュだけを残す。これで足りるかは弁護士に確認する。

### 改ざん防止だけでは防げないこと

| 問題 | 対策案 | 状態 |
| --- | --- | --- |
| 都合の悪い履歴を隠す | 件数や結果の集計を、個別の取引を明かさずに証明する（ゼロ知識証明など） | 未決。匿名性と正面からぶつかる |
| 架空の取引で実績を作る | 支払いの証明と結びつけ、評判が高い相手や多様な相手からの実績を重く見る | 計算方法は各Agentが決める。完全には防げない |
| 入力そのものが嘘 | 評判とローカルルールの紛争解決で補う | 納品の品質など、仕組みの外の事実は証明できない |

## ローカルルール

契約は国や業界ごとに異なるため、共通仕様には入れない。共通仕様が決めるのは、ローカルルールへの渡し方だけ。

- **指定の仕方**: 依頼票の `localRules` に、ルールのIDとバージョンを書く。例: `jp-freelance/1.0`
- **公開するもの**: 合意案に追加する項目（`localTerms`）の定義、適用される地域と業種、開発者、合意のあとの手続き。
- **ルールが決めること**: 法定の明示事項、契約書の形式、支払いとエスクロー、税、検収、紛争解決。
- **選ぶのは人間**: 知らないルールや信じていないルールなら、Agentは交渉に入らない。合意案には、どのルールが適用されるかを必ず表示する。
- **責任**: ルールが法律に合っているかは、開発者と利用者の側の責任になる。範囲は弁護士に確認する。

最初の参照実装として、日本の業務委託向けに `jp-freelance` を作る案がある。業務内容・報酬額・支払期日などフリーランス保護法で明示が必要な事項を必須にする（弁護士の確認前の仮）。

## 未決事項

- **タグの語彙**: スキルの分類にどの公開の体系（ESCOなど）を基本にするか。独自タグの名前空間が乱立したときにどう寄せるか。
- **最初のノード一覧**: 初めて使う人が問い合わせる中継ノードの一覧を、誰がどう配るか。既定の一覧が事実上の中心にならないようにする方法。
- **スパム対策**: 誰でも依頼票を出せる状態で、偽の案件や大量発行をどう抑えるか（発行回数の制限、評判、少額の供託など）。
- **台帳の方式**: 定期的な記録にどの公開チェーンを使うか。透明性ログの運営と記録の費用を誰が負担するか。監視ノードを何台必要とするか。
- **ハッシュと個人情報**: 証明のハッシュが個人情報にあたるかどうか（弁護士の確認が必要）。
- **鍵をなくしたとき**: 人間が鍵を失った場合の復旧の方法。
- **ノードの運営費**: 誰がどのような動機でノードを運営するか。
- **広告化の防止**: 表示順位を売るノードを仕様では禁じられない。買われた順位をどう見分けるか。
- **AIによる自警の範囲**: どこまで自動で実行し、どこから人間に確認するか。
- **拡張URIの管理**: w3id.org の登録（a2a-job は仮の名前）を誰が持つか。1人にせず、複数の管理者で持つ形にするか。
- **委任範囲の形式**: Mandate を AP2 の委任書にどこまで合わせるか。署名は JCS＋JWS とした。
- **同時交渉の上限**: 1件の依頼票で同時に交渉できる候補の数。
- **契約後の扱い**: 進捗報告・納品・検収を共通の拡張にするか、ローカルルールに任せるか。
- **外部システムへの受け渡し**: 契約・支払いのシステムに渡す証拠一式の形式。1つのファイルにまとめるか、どの外部システム（電子契約、請求、エスクロー）を最初の受け手にするか。受け手が IX のノードを使わずに署名と履歴のつながりを確かめる手順。

* **履歴の隠蔽**: 都合の悪い履歴を隠せないようにしつつ、匿名性を保つ方法。実績をどこまで見せるか。
* **結果登録の乱用**: `disputed` を乱用して相手の評判を下げる行為をどう扱うか。

# 副業人材への誘い文句（案）

誘いの核は「探しに行かなくていい。CMOが直接頼みたい仕事が、あなたの条件に合うときだけ届く」。手数料無料より先に、手間がなくなることと仕事の質を伝える。対象は招待する優秀な副業人有30人で、登録率30%を目指す。

## 伝える順番

1. **なぜあなたに声をかけたか**: 実績や投稿など、その人だけの理由を最初に書く。
2. **何が届くか**: 採用で困っているCMOからの仕事が、条件に合うときだけ届く。
3. **やること**: 5分の登録と、届いた合意案を受けるかどうか決めることだけ。
4. **縛られない**: 受けるかは毎回本人が決める。手数料は無料で、いつでもやめられる。
5. **招待制の試験運用**: 30人限定で、率直な感想も欲しい。

## 文案A: 知人向け（LINE・Messenger、長め）

> &#91;名前\]さん、お久しぶりです。\[自分の名前\]です。
>
> いまCMOとして採用を続けているのですが、良い人ほど採用市場にいなくて、外に頼みたい仕事が社内にたまっています。同じ悩みを持つCMO仲間も多いです。
>
> そこで、副業で力を貸してくれる人と、そういう仕事をつなぐ仕組みを試しています。\[名前\]さんの\[得意分野・過去の仕事\]を思い出して、真っ先に声をかけたいと思いました。
>
> 仕組みはシンプルです。 ・5分ほどで、得意分野・単価の下限・使える時間・やらない仕事を登録する ・あとはAIのAgentが、条件に合う仕事が来たときだけ相手と条件を詰めて、合意案を届ける ・受けるかどうかは毎回\[名前\]さんが決める。手数料はかからない
>
> いまは30人限定の招待制で試しているところです。興味があれば登録リンクを送ります。率直な感想だけでも嬉しいです。

## 文案B: SNSのDM（X・LinkedIn、短め）

> &#91;名前\]さん、突然すみません。\[会社名\]でCMOをしている\[自分の名前\]です。\[名前\]さんの\[実績・投稿\]を拝見してご連絡しました。
>
> 採用できずに止まっているマーケ・デザインの仕事を、副業の専門家に届ける仕組みを試しています。条件（単価の下限・時間・やらない仕事）を登録しておくと、AIのAgentが合う仕事だけ交渉して届けます。受けるかは毎回ご本人が決め、手数料は無料です。
>
> 30人限定で試しています。ご興味があれば、詳細をお送りしてもよいでしょうか。

## 文案C: 返信がない場合（1週間後、1回だけ）

> 先日の件、押し付けるつもりはありません。もし「こういう条件なら受けたい」という仕事のイメージがあれば、一言だけでも教えていただけると、仕組みづくりの参考になります。

## 5分登録の項目

単価の下限とやらない仕事は相手に見せず、Agentの委任範囲としてだけ使う。このことを登録画面に明記する。

| 項目 | 入力の形 | 使い道 |
| --- | --- | --- |
| 経歴・実績のURL | URL（LinkedIn、ポートフォリオなど） | Agentの自己紹介と実績の根拠 |
| 得意分野 | 選択（最大3つ）＋ひとこと | 依頼票との照合 |
| 単価の下限 | 時給または案件単価（円） | 委任範囲の下限。これ未満では合意しない |
| 使える時間 | 週あたりの時間、平日夜・週末など | 納期と稼働の照合 |
| やらない仕事 | 自由記述（例: 本業の競合、成果報酬のみ、常駐） | 委任範囲から外す |
| 連絡の受け方 | Slack・LINE・メールから選ぶ | 合意案の承認依頼を届ける先 |
| 本業との関係 | 確認のチェック（副業規定、競業の制限） | トラブルの防止 |
| 自前のエージェント（任意） | Agent CardのURL | 持ち込みの割合を測る |

## よくある懸念と答え

| 懸念 | 答え |
| --- | --- |
| AIが勝手に契約しない？ | 契約は必ずあなたの承認の後。Agentはあなたが決めた条件の外では合意できない |
| 本業に知られない？ | 成約まで氏名や会社名を相手に出さず、表示名と実績だけを見せる。副業規定はご自身で確認を |
| 結局安い仕事ばかりでは？ | 下限未満の仕事は届かない。発注者は採用で困っているCMOで、単価より手間の削減を重んじる |
| 手数料は？ | 受注者は無料。手数料は発注者が払う |
| 時間を取られない？ | やることは受けるかどうかを決めることだけ。断っても評価は下がらない |

## 言わないこと

- **収入の約束**（「月◯万円稼げる」など）: 実績がない段階では誤解を招く。
- **「採用」「雇用」**: 扱うのは業務委託。
- **発注企業の名前**: 相手の了承なしに出さない。

## 測ること

- 文案A・Bごとの返信率と登録率（目標: 登録率30%）
- 登録しなかった人の理由（一言で聞く）
- 登録が終わるまでに実際にかかった時間
